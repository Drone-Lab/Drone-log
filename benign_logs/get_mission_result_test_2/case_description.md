"vulnerabilities": "1. In AUTO_RTL you trigger the mission to run in REVERSE mode; Mission::set_execution_mode(REVERSE) runs but does not publish the change yet.  \n2. Immediately switch back to AUTO_MISSION (normal mode); Mission::set_execution_mode(NORMAL) runs, but again the result is not published.  \n3. Navigator::run() still sees _mission_execution_mode as REVERSE when handling the next mission item, so it flies the waypoint in the wrong order until the next seq_current/seq_reached update forces a publication of the new mode.",
"thoughts": "Mission::set_execution_mode() updates the in‐memory _mission_execution_mode and writes the new mode into mission_result.execution_mode, but it does not call _navigator->set_mission_result_updated(). Therefore the change to execution_mode is not immediately flagged for publication. Until the next call to set_current_mission_item() or set_mission_item_reached(), the ORB publication of mission_result still carries the old execution_mode value. Meanwhile, the Navigator logic that picks the next work item type relies on the stale _mission_execution_mode. This can cause the mission to continue executing in reverse when the user has just requested normal forward execution, or vice versa."
